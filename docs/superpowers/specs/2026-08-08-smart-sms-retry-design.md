# 智能短信重试与风控熔断设计

## 背景

2026-08-08 的最近五次手机号验证任务在 35 次取号尝试中取得 30 个号码，结果为 24 次 `fraud_guard`、4 次 `rate_limited`、2 次 `number_in_use`，另有 5 次 `NO_NUMBERS`。所有已取得号码都在 OpenAI 接受短信发送之前失败，短信发送、收码和验证成功次数均为 0。

现有上游流程把大多数手机号失败统一处理为“取消号码、等待数秒、继续换号”，因此一个任务可能连续消耗 5 至 10 个号码，并在连续风控拒绝后进一步触发限流。

## 目标

- 按明确失败类型决定停止或有限换号。
- 第一次 `fraud_guard` 或手机号接口 `rate_limited` 后停止当前账号任务。
- 只在号码自身问题或短信投递问题上允许有限换号。
- 保持成功的短信发送、收码和验证流程不变。
- 不修改两个上游项目的受同步文件，避免阻塞 GitHub 上游更新。
- 日志和统计继续隐藏完整手机号、验证码、API Key 和其他凭据。

## 非目标

- 不实现代理轮换、浏览器指纹伪装或其他风控绕过能力。
- 不自动调整最低价、最高价、指定价格档或国家队列。
- 不保证接码平台号码能通过 OpenAI 的账号或号码资格检查。
- 不修改未被当前统一管理器调用的上游 OAuth 驱动。
- 不让失败账号自动绕过人工判断反复运行。

## 已考虑方案

### 方案一：直接修改上游 OAuth 文件

实现最直接，但会让 vendored 上游文件偏离锁定快照。更新管理器会把这种偏离视为本地上游修改，从而阻止或回滚更新，不符合持续同步 GitHub 的要求。

### 方案二：修改接码项目的 `src/` 核心文件

运行路径清晰，但这些文件同样属于接码项目上游清单。以后上游更新会产生所有权冲突，必须长期维护补丁。

### 方案三：统一管理器覆盖层

这是采用的方案。智能重试实现放在受保护的 `manager/` 集成层，由 `manager_app.py` 在统一管理器启动及 Windows worker 子进程导入阶段安装。运行时临时覆盖当前实际使用的 `core.codex_oauth` 手机验证函数；任务结束或进程退出后不写回 vendored 文件。

该方案保持两个上游快照原样，代价是优化只保证作用于 `启动.cmd` / `manager_app.py` 的统一管理器入口。直接运行上游 `python app.py` 时仍使用上游原始策略。

## 架构与组件

### `manager/sms_retry_policy.py`

提供不依赖网络和上游模块的纯决策逻辑。输入包括失败阶段、标准化失败原因、该原因已发生次数、当前总取号次数和配置总上限；输出为停止、换号或成功继续，以及稳定的结果代码和用户可读日志文本。

策略本身不睡眠、不购买号码、不取消号码，也不读取环境变量，便于独立测试。

### `manager/sms_runtime_overlay.py`

负责把策略接到当前上游运行时：

- 验证上游所需函数和异常类型仍然存在。
- 为当前 worker 安装一次幂等的手机号验证覆盖函数。
- 复用上游的 HTTP、会话、响应解析和 OTP 校验能力。
- 复用本项目已有的 HeroSMS 获取、取消、完成和轮询适配器。
- 在结束前尽力取消当前 activation；取消失败只记录脱敏警告，不改变原始停止决定。
- 抛出带稳定机器代码的本地异常，使调度器区分风控、限流、无号码和普通失败。

覆盖层不得修改 vendored 文件，不得在日志中输出完整手机号、API Key、短信验证码或原始敏感响应。

### `manager_app.py`

在导入并创建统一管理器应用时安装覆盖层。安装必须幂等，兼容 Flask 调试重载和 Windows `multiprocessing` 的 spawn 导入流程。

### 调度结果映射

统一管理器把 `phone_fraud_guard`、`phone_rate_limited` 和 `sms_no_numbers` 标记为当前账号不可自动重试。`number_in_use` 和短信超时的有限换号在 worker 内完成，不升级为整个账号任务的自动重跑。

流水线中的其他账号不因单个账号熔断而停止。失败账号之后仍可由用户手动重新发起。

## 决策规则

| 失败情况 | 动作 | 单个账号任务内上限 |
|---|---|---:|
| `fraud_guard` / suspicious behavior | 取消当前号码并立即停止 | 1 个号码 |
| 手机号接口 `rate_limited` | 取消当前号码并立即停止，不自动重跑 | 1 个号码 |
| `number_in_use` / phone used | 取消并允许换号一次 | 2 个号码 |
| 短信已成功请求但收码超时 | 取消并允许换号一次 | 2 个号码 |
| OTP 校验被拒 | 取消并允许换号一次 | 2 个号码 |
| HeroSMS `NO_NUMBERS` | 立即停止 | 1 次完整国家/价格队列扫描 |
| HeroSMS 余额不足或 API Key 错误 | 立即停止 | 1 次 |
| 明确的临时服务端错误 | 允许换号一次 | 2 个号码 |
| 未知短信发送错误 | 允许换号一次后停止 | 2 个号码 |
| 验证成功 | 完成 activation 并继续 OAuth | 不适用 |

现有 `SMS_MAX_RETRIES` 保留为绝对总上限。决策表中的较小上限优先，不能通过把 `SMS_MAX_RETRIES` 调大来绕过熔断。

`HeroSmsAdapter.acquire_number()` 已在一次调用内依次尝试配置的国家和合格价格档，因此外层收到 `NO_NUMBERS` 后不得再次进行相同队列扫描。

## 数据流

1. worker 进入手机号验证，读取现有 `SMS_MAX_RETRIES` 总上限。
2. HeroSMS 适配器按现有国家和价格策略尝试取得一个 activation。
3. worker 把号码提交到 OpenAI `add-phone/send`。
4. 覆盖层从 HTTP 状态和脱敏响应文本生成标准化失败原因。
5. 纯策略函数返回停止或换号决定。
6. 停止或换号前，覆盖层尽力取消当前 activation。
7. 短信发送被接受时，覆盖层通知 HeroSMS、轮询验证码并提交 OTP。
8. 验证成功后完成 activation，继续原有 OAuth 流程。
9. 终止决定以稳定错误代码返回调度器，调度器更新任务状态和 WebUI 日志。

## 日志与用户体验

新增日志应使用稳定、可检索且不含敏感数据的消息：

- `风控熔断：已取消当前号码，停止当前账号任务`
- `手机号接口限流：停止当前账号任务，不自动重试`
- `号码已使用：允许换号 1/1`
- `短信收码超时：允许换号 1/1`
- `HeroSMS 无可用号码：已扫描配置队列，停止任务`

现有接码统计继续从日志识别 `fraud_guard`、`rate_limited`、`number_in_use`、`sms_timeout` 和 `verified`。新增停止文本必须保持这些标准化状态可识别。

## 错误处理

- activation 创建后，所有停止分支都必须在退出前尝试取消。
- 取消失败不得掩盖触发停止的原始原因，也不得再次购买号码。
- HeroSMS 余额不足、凭据错误和无号码属于非自动重试错误。
- 手机号限流只停止当前账号；不得让调度器在固定 180 秒后自动重跑该账号。
- 覆盖层发现上游函数签名或必要属性不兼容时应明确失败，禁止静默回退到无限换号的上游行为。
- 成功完成 activation 后不得再调用取消。

## 上游更新兼容性

- 新增实现只位于锁文件保护的 `manager/` 前缀和统一管理器入口。
- 不修改 `vendor/turb-gpt-free-register/`、`src/` 或其他 receiver 上游清单文件。
- 上游更新测试必须验证覆盖层仍能识别并安装到实际使用的 `core.codex_oauth`。
- 若上游删除、重命名或改变必要接口，更新流程的 Python 测试必须失败，现有更新脚本据此回滚文件、依赖和服务。
- 直接执行上游 `app.py` 不承诺启用本策略；本地文档必须说明应使用现有启动开关。

## 测试策略

### 决策单元测试

- 第一次 `fraud_guard` 返回停止。
- 第一次手机号 `rate_limited` 返回停止。
- `number_in_use` 只允许一次换号。
- 短信超时只允许一次换号。
- `NO_NUMBERS` 返回停止。
- 未知错误只允许一次换号。
- `SMS_MAX_RETRIES` 比策略上限更小时，以配置总上限为准。

### 运行时覆盖测试

使用假的上游模块、HTTP 响应和 HeroSMS 生命周期函数验证：

- 风控和限流均在取消一个 activation 后退出。
- 号码已使用第一次换号、第二次退出。
- 短信超时第一次换号、第二次退出。
- `NO_NUMBERS` 不再次调用取号。
- 取消失败保留原始停止代码。
- 成功路径调用 set status、收码、校验和 complete，且不调用 cancel。
- 安装两次不会重复包装。
- 上游必要接口缺失时安装或运行明确失败。

### 调度与集成测试

- `phone_fraud_guard`、`phone_rate_limited` 和 `sms_no_numbers` 均不可自动重试。
- 其他账号在流水线中仍可继续。
- WebUI 与日志只显示脱敏结果。
- `manager_app.py` 在 Windows spawn 子进程导入场景中安装覆盖层。
- 完整 Python 测试套件、转换器 Node 测试和本地 `/health` 冒烟测试通过。

## 验收标准

- 第一次 `fraud_guard` 后最多消耗一个号码。
- 第一次手机号 `rate_limited` 后停止，调度器不自动重跑该账号。
- `number_in_use`、短信超时和 OTP 拒绝最多各换号一次。
- `NO_NUMBERS` 不再重复五至十次相同扫描。
- 正常短信发送、收码、OTP 验证和 OAuth 后续流程保持可用。
- 日志和 API 不泄露完整手机号、验证码、API Key 或原始敏感响应。
- 上游受同步文件保持未修改，更新兼容测试可阻止不兼容版本上线。
