# 两项目安全同步更新设计

## 目标

让本地统一管理环境能够持续跟踪两个 GitHub 上游，同时保护本地配置、业务数据和统一管理适配层。管理页自动执行只读更新检查；实际更新必须由使用者明确启动本地更新按钮，并经过预检、备份、校验、测试、回滚和重启门槛。

## 为什么不使用普通自动 `git pull`

当前 Codex Auto SMS Receiver 是在本机 Git HTTPS 克隆连续失败后，从 GitHub 官方 codeload 快照导入并初始化的本地历史，与上游 Git 提交图没有共同祖先。直接 `git pull` 会产生无关历史合并或覆盖风险。第二个项目又需要保持为可整目录替换的独立快照。

因此同步器使用 GitHub API、递归 Git tree 和按提交 SHA 下载的官方 codeload 包，按文件归属清单更新，而不依赖本机 Git 历史是否与上游相连。

## 文件归属模型

`manager/upstreams.lock.json` 为受版本控制的锁文件，每个上游包含：

- 仓库全名、分支、当前完整提交 SHA。
- 部署目标：当前仓库根目录或 `vendor/GPTSession2CPAandSub2API/`。
- 当前 Git tree 中的文件路径、类型、大小和 blob SHA。
- 本地所有路径清单与禁止碰撞的集成路径前缀。

当前项目的上游文件保持原样。此前加入上游 `README.md` 的本地部署说明迁移到 `LOCAL-DEPLOYMENT.md`，随后恢复上游 README 内容，使根项目的上游文件能够通过 blob SHA 预检。统一管理代码、Windows 按钮、`manager/`、Superpowers 文档和本地测试属于集成层，不在上游替换清单中。

## 用户入口

- 管理页加载时调用只读状态接口，比较锁定 SHA 与 GitHub 主分支最新 SHA；结果缓存 10 分钟，网络失败只显示“无法检查”。
- `检查更新.cmd` 调用 `ops/upstream/Check-Upstreams.ps1`，输出两个项目的当前 SHA、最新 SHA和最近提交标题，不修改文件。
- `更新两个项目.cmd` 调用 `ops/upstream/Update-Upstreams.ps1`，支持更新全部或通过参数只更新一个项目。双击默认先显示预览并要求明确确认。
- 浏览器管理页不提供自修改源码的 POST 接口，避免一个无认证 WebUI 请求直接触发源码替换。

PowerShell 入口只负责 Windows 双击体验和调用项目虚拟环境。下载、Git blob 校验、清单比较、备份、应用和回滚由可测试的 `manager/upstream_sync.py` 实现。

## 只读检查流程

1. 使用带超时和明确 User-Agent 的 GitHub API 请求读取每个仓库主分支最新提交。
2. 与锁文件中的完整 SHA 比较。
3. 有更新时读取最新提交标题和时间，但不下载归档、不停止服务、不修改锁文件。
4. API 限流、离线或响应格式错误时返回非敏感错误状态；服务其他功能继续可用。

## 更新预检

更新开始前必须全部通过：

- 工作目录、目标目录和备份目录解析后均位于项目根目录内。
- `.env`、`.venv`、`data/` 和 `logs/` 不在任何上游文件清单内。
- 当前上游管理文件的 Git blob SHA 与锁文件一致；发现本地手工修改时停止并列出路径，不自动覆盖。
- 最新 Git tree 中没有文件与集成层保留路径碰撞；碰撞时停止并要求人工设计迁移。
- 当前服务 PID 必须能通过项目入口和虚拟环境父子进程校验，才能由更新脚本自动停止。

## 下载和内容校验

同步器先通过 GitHub API解析最新完整 SHA，再使用该 SHA 的 codeload URL 下载归档到 `data/upstream-staging/<transaction-id>/`。下载支持超时、重试和可诊断错误。

解压后对照 GitHub `git/trees/<sha>?recursive=1`：

- 拒绝符号链接、子模块和目标目录之外的路径。
- 对每个普通文件计算 Git blob SHA（`sha1("blob <size>\0" + content)`）并与 tree 响应一致。
- 文件数量、路径、大小和 blob SHA 全部匹配后，归档才可进入应用阶段。

## 备份、应用和依赖

更新事务备份到 `data/upstream-backups/<timestamp>-<transaction-id>/`，包括旧锁文件、所有将被替换或删除的上游文件以及第二项目的旧快照。业务数据不复制也不修改。

归档和 Git tree 校验可以在服务运行时完成。备份完成后、写入任何上游文件之前，更新器必须通过项目进程身份校验安全停止服务；无法证明 PID 归属或无法停止时，事务在修改源码前终止。

应用规则：

- 当前项目只新增、替换或删除锁文件所声明的上游路径。
- 第二项目的 vendor 目标使用已校验的新快照整目录替换。
- 集成层路径永不由同步器写入或删除。
- 锁文件只在内容校验和文件应用完成后写入临时文件并原子替换。

如果 `requirements.txt` 没有变化，复用现有 `.venv`。如果依赖变化，在停止服务前先用 staging 中的新依赖，在 `.venv-next` 中从当前虚拟环境记录的基础 Python 创建新环境并安装 pytest。服务停止后把旧 `.venv` 改名为事务专属的 previous 目录，再把 `.venv-next` 原子切换为 `.venv`；旧环境在所有测试和重启验证成功前保持不动，失败时切回旧环境。

## 测试门槛和重启

更新应用后依次运行：

1. 新环境或现有环境中的完整 `python -m pytest -q`。
2. `node vendor/GPTSession2CPAandSub2API/tests/convert-session.test.js`。
3. 组合入口的离线导入和路由冒烟测试。

所有测试通过后启动 `manager_app.py`，等待 `/health` 和 `/manager` 成功。只有启动验证通过，事务才标记为成功。同步器不自动创建 Git 提交或推送远端；本地源码变化保留供使用者检查。

## 回滚

以下任一情况触发回滚：内容校验失败、文件应用失败、Python 测试失败、Node 测试失败、新虚拟环境失败或重启健康检查失败。

回滚按备份清单恢复旧文件、删除本事务新增的上游文件、恢复旧 vendor 快照和旧锁文件；如果切换过虚拟环境则恢复旧 `.venv`。恢复后使用旧组合入口重新启动并验证 `/health`。回滚失败时停止继续操作，保留备份和事务日志，并输出需要人工处理的确切路径。

## 安全和日志

- 更新器只访问 `api.github.com`、`codeload.github.com` 和安装依赖时锁文件允许的 Python 包索引。
- 更新日志保存在 `data/upstream-update-logs/`，不得包含 `.env`、Token、账号素材或凭证文件内容。
- 更新器不读取或备份 `data/codex_accounts/` 等业务数据。
- 备份与 staging 均在已经被 Git 忽略的 `data/` 内，成功事务会清理 staging；备份默认保留最近 3 次。

## 测试与验收

- Python 单元测试使用临时工作区、伪造 Git tree 和本地 ZIP，覆盖无更新、更新、文件新增/删除、blob 不匹配、路径穿越、集成路径碰撞和本地漂移。
- 事务测试覆盖应用成功、Python 测试失败、Node 测试失败、重启失败和完整回滚。
- PowerShell/CMD 行为测试验证从无关当前目录执行、只读检查不写文件、失败时返回非零和更新确认门槛。
- 使用真实 GitHub API 做一次只读检查，确认两个锁定 SHA 与当前主分支一致。
- 最终实际运行 `检查更新.cmd`，确认当前显示“已是最新”，且 `git status`、服务 PID 和业务数据均未改变。

## 不在本阶段范围内

- 不定时自动安装更新，不在启动时自动覆盖源码。
- 不自动合并本地手工修改过的上游文件。
- 不自动提交、推送或创建 Pull Request。
- 不绕过失败测试强行保留新版本。
